# Reframe Constitution

> **Reframe** — приватный голосовой дневник для профессионалов, испытывающих высокий уровень стресса. Цель — помочь пользователю дистанцироваться от эмоционально заряженных ситуаций через когнитивный рефрейминг.

## Терапевтическая основа

Методология рефрейминга опирается на когнитивно-поведенческую терапию (КПТ) и труд Дэвида Бёрнса **«Терапия настроения»** (David D. Burns, *Feeling Good: The New Mood Therapy*). Ключевые техники:

- Выявление и оспаривание когнитивных искажений (catastrophizing, black-and-white thinking, mind reading и др.)
- Техника трёх колонок: автоматическая мысль → когнитивное искажение → рациональный ответ
- Разделение фактов и интерпретаций
- Сократический диалог для самостоятельного переосмысления ситуации

Промпты LLM строятся на основе структурированных техник из книги, адаптированных под голосовой формат взаимодействия.

## Core Principles

### I. Приватность — Данные только на устройстве (НЕНАРУШИМО)

Все записи дневника, голосовые заметки и настройки хранятся исключительно на устройстве пользователя. Бэкенд не имеет базы данных и не сохраняет пользовательский контент ни в каком виде.

**Запрещено**: серверное логирование текстов записей, аналитика с раскрытием содержимого, любая телеметрия, способная идентифицировать содержание записей пользователя.

### II. Простота — Минимализм интерфейса

Успокаивающий, лаконичный интерфейс без визуального шума. Каждый элемент на экране должен быть оправдан. Никаких туториалов, онбордингов, повторяющихся подсказок. Единственное исключение — однократный оверлей при первом запуске, объясняющий базовый цикл «оценка тревоги → рассказ → рефрейминг». Пользователь должен интуитивно понимать, что делать, без чтения инструкций. Максимум 2–3 видимых действия на экране одновременно.

### III. Скорость — Быстрый ответ LLM (дополнен v2)

Ответ LLM должен ощущаться отзывчивым. Для одиночного агента (v1) — без заметного «пустого» ожидания. Для multi-agent (v2) допустима большая суммарная latency: пользователь видит progressive feedback (карточки агентов появляются по мере готовности, agent-complete SSE), а не пустой экран. Значительные задержки без обратной связи считаются ошибкой производительности.

### IV. Человекоцентричность — Доброжелательный дизайн

Тёплая нейтральная палитра (песочные, кремовые, мягкие серые тона). Ориентиры: Calm (calm.com) — тёмные глубокие тона, одно действие на экран; Headspace (headspace.com) — тёплые акценты, дружелюбные иллюстрации; Nivra (nivra.app) — минимализм, тёмная тема, «тихий» интерфейс без навязчивости. Крупные кнопки и зоны касания (минимум 48px). Минимум текста — интерфейс говорит иконками, жестами и голосом. Тёмная тема по умолчанию с возможностью переключения на светлую. Интерфейс адаптирован под голосовое взаимодействие — большие элементы управления, визуальная обратная связь на голосовой ввод.

### V. Test-First (TDD) — см. Процесс разработки.

### VI. Контракт-Фёрст — LLM как внешний сервис (дополнен v2)

Контракт взаимодействия с LLM определяется на бэкенде для каждого агента независимо. Фронтенд не знает деталей LLM-провайдера — только унифицированный API. Замена одного агента не затрагивает других агентов или фронтенд. Бэкенд отвечает за форматирование промптов, ответа LLM, таймауты и retry. LLM-провайдер заменяем без изменения фронтенда.

### VII. Расширяемая архитектура (v2)

Архитектура агентов открыта для расширения. Новый агент добавляется одной записью в реестр + один промпт — без изменений в ядре системы. Фронтенд динамически рендерит любое количество агентов.

## Архитектура

### Бэкенд — тонкий прокси

Бэкенд — тонкий прокси с элементами бизнес-логики: принимает запрос от клиента, выполняет промпт-инжиниринг (методология Бёрнса, классификация искажений, формат рефрейминга), передаёт LLM-провайдеру, возвращает ответ LLM клиенту.

Бизнес-логика распределена: клиент отвечает за валидацию ввода, управление сессией, историю записей и пользовательский опыт; бэкенд — за промпт-инжиниринг (методология Бёрнса, классификация искажений, формат рефрейминга).

### Границы

| Компонент | Отвечает за | НЕ отвечает за |
|---|---|---|
| Фронтенд | UI, голосовой ввод, хранение записей, клиентскую бизнес-логику | Ключи API, прямой доступ к LLM, раскрытие модели провайдера |
| Бэкенд | Прокси к LLM, промпт-инжиниринг (КПТ/Бёрнс), ответ LLM | Хранение данных, логирование содержимого, базу данных |

## Процесс разработки

### Pre-commit gates

Перед каждым коммитом код проходит автоматическую проверку: типы чисты, линтер чист, тесты зелены. Коммит, не прошедший проверку, не допускается.

### TDD

Каждая функция начинается с падающего теста. Red-Green-Refactor строго. Без тестов production-код не пишется.

### Ревью

Изменения, затрагивающие конституцию, архитектуру или контракты API — через PR с явным обоснованием.

### Качество кода

E2E-тесты основного сценария проходят. CI работает без регрессий. Никакого мёртвого кода, закомментированных блоков, TODO без привязанных задач. TypeScript: никаких `any` в production-коде. Для браузерных API без встроенных типов — использовать `@types/*` пакеты.

## Управление изменениями

Конституция — верховный документ проекта. Любое архитектурное или процессное решение, противоречащее конституции, требует её изменения до начала реализации. Изменения конституции — через PR с явным обоснованием.
